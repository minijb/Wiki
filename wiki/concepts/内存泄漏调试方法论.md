# 内存泄漏调试方法论

Unity（尤其 C#↔Lua 混合栈）资源泄漏调试的系统化方法：**找到"钉住源"，再判断它是否致命**。核心是两条能力——沿引用链反推根因，以及辨析根因与次要因素。本文从 [[sources/spine-texture-leak-gongsunyue-摘要|一个 16 MB Spine 纹理泄漏案例]]抽象而成。

## 核心思想

泄漏 = 资源本应释放却仍存活 = **存在一条未被切断的引用链**把资源钉在内存里。调试就是：

1. 抓内存快照，沿 `Referenced By` **逆引用链**回溯，定位链的起点（钉住源）。
2. 判断这条链是**致命的**（根因，必须切断）还是**可被绕过/回收的**（次要因素）。
3. 在正确的释放点（通常是 `OnDestroy` / `Dispose`）切断根因链，验证资源释放。

## 引用链反推根因法

### 步骤

```
① 内存快照搜索泄漏对象名（如 Texture2D: paintinganim_xxx）
② 展开 Referenced By，逐层向上看谁持有它
③ 画出完整引用链，直到链的根（LuaEnv / GC root / static）
④ 在链上找"本应断开却没断开"的那一环 = 钉住源
```

### 决定性判据：用"已知前提"反推

最快锁定根因的方式是利用**确定不移的前提**做反证。典型案例：

> [!example] Spine 纹理泄漏的反推
> 前提：截图时 GameObject **已被销毁**。
> 推论：Unity 中 `GameObject.Destroy` 必然触发 MonoBehaviour 的 `OnDestroy` ⇒ `OnDestroy` **一定执行过**。
> 事实：纹理仍在内存。
> 结论：**唯一可能是 `OnDestroy` 没有释放纹理**。
>
> 这条反推把排查范围从"整个系统"收窄到"`OnDestroy` 函数体"——根因必在其中。

> [!tip] 何时能做反推
> 当快照能证明某个"必然执行的释放路径"已经走过（GO 已销毁、对象已 Dispose、计数已归零），而资源仍在，则泄漏点**必在该路径的实现里**。无需通读全部代码。

## Unity 泄漏三层模型

理解泄漏必须区分三层——它们的生命周期**不同步**，这是大多数泄漏的根源。

| 层 | 对象 | 销毁方式 | 关键特性 |
|----|------|----------|----------|
| 原生对象 | GameObject、Component、Texture2D（原生部分） | `Destroy` / `DestroyImmediate` | 销毁后 C# 包装变 fake null |
| 托管包装 | MonoBehaviour 子类、自定义 C# 类 | .NET GC | fake null 后**仍存活**，字段引用仍在 |
| 资源资产 | AssetBundle 加载的 Material/Texture | 引用计数 / `Resources.UnloadAsset` | 计数不归零则不释放 |

> [!warning] fake null 不等于回收
> `Destroy(go)` 把 C# 包装的 `m_CachedPtr` 清零（与 `null` 比较相等），但**托管对象本身仍在堆上**，其字段引用依旧有效。只要 .NET GC 没跑，被它引用的资源就不会被回收。这意味着：一个被外部（如 xLua 桥）强引用钉住的托管包装，即便其 GameObject 已销毁，仍可持续持有原生资源。

> [!note] 释放点必须在 OnDestroy / Dispose
> 因为 fake null 的托管包装可能长期存活，**资源释放不能依赖 GC**，必须在 `OnDestroy`（GO 销毁时必然触发）或 `Dispose`（显式调用）里**主动断开所有资源引用**。这是 [[concepts/Spine资源管理|Spine 资源管理]] 清理三步法存在的根本原因。

## xLua 对象桥钉住

C#↔Lua 混合栈的特有放大器。详见 [[concepts/XLua热补丁|XLua 热补丁]]。

- xLua 把每个被 Lua 访问过的 C# 对象以**强引用**存入 `ObjectTranslator.objects`（键即 C# 对象本身）。
- 只要 Lua 侧还有任何引用（字段、闭包 upvalue、表项），C# 对象就留在桥缓存，.NET GC 无法回收。
- 解除钉住：先断开 Lua 侧**所有**引用 → Lua GC 触发 userdata `__gc` → 移除桥缓存项 → C# 对象可被 .NET GC 回收。

> [!important] 钉住通常只是"次要因素"
> 桥钉住让一个**小的** C# 包装对象长期存活。但它本身不持有大资源——致命的是"存活的小对象**沿字段引用到达大资源**"。因此治本之道是**在释放点断开大资源引用**（让小对象即使存活也碰不到资源），而不是去和桥的 GC 时机搏斗。[[sources/spine-texture-leak-gongsunyue-摘要|Spine 案例]]中 xLua 钉住 `SpineUIController2` 是次要因素，根因是该对象没在 `OnDestroy` 置空 `skeletonGraphic` 字段。

## 根因 vs 次要因素辨析

泄漏现场常有多个"看起来都相关"的问题。误把次要因素当根因会导致**改了不该改的、漏了该改的**。

> [!success] 判定标准：去掉它，问题是否消失
> 根因 = 移除后泄漏消除。次要因素 = 移除后泄漏仍在，只是延缓/缩小。
> 验证方法：**只**修疑似根因那一点，复测。若泄漏消失 ⇒ 确认根因；若仍在 ⇒ 它不是根因，继续找。

> [!failure] Spine 案例的误判教训
> 早期分析把"消费者面板不主动回收 `avatarSpine`"判为治本根因（P0）。但实际修复**根本没碰**这一点，只改了 C# `OnDestroy` 的纹理释放，泄漏即消除——反证前者只是次要因素。
> 误判信号：建议改的代码改完仍有泄漏，或实际修复路径与建议完全不同却生效。出现时必须回头重新辨析根因。

### 常见的次要因素（勿当根因）

- GC 时机问题（Lua GC / .NET GC 延迟回收）——属"及时性"，非"泄漏"。
- 对象池/缓存延长存活——只要最终能回收，非永久泄漏。
- 桥/弱引用钉住小对象——只要释放点断开大资源引用，钉住无害。

## 排查清单

面对一次疑似泄漏，按序检查：

- [ ] 快照搜泄漏对象名，展开 `Referenced By` 画引用链到根。
- [ ] 链上有无"已执行释放路径但资源仍在"的环节？（→ 反推锁定实现）
- [ ] 托管包装是否被外部强引用钉住（xLua 桥、static、事件订阅、闭包）？
- [ ] 释放点（`OnDestroy`/`Dispose`）是否**完整**断开了所有资源引用（不止 mainTexture，还有 CanvasRenderer 槽、字段、引用计数）？
- [ ] 引用计数型资源（AssetBundle 加载）的 `UnloadAsync` 是否被调用？
- [ ] 释放逻辑是否有早退/NRE 路径跳过关键置空？（空判缺失导致中断）
- [ ] 区分：这是永久泄漏，还是 GC/超时延迟回收？
