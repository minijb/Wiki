# 帧同步 vs 状态同步

实时多人游戏中两种核心网络同步模型：**帧同步**（Lockstep）仅在客户端间传输操作指令，各端独立执行确定性逻辑；**状态同步**由服务器计算权威结果并广播状态给客户端。从带宽、确定性、延迟、反作弊和适用场景五个维度做深度对比。

## 核心原理

### 帧同步（Lockstep / Frame Sync）

客户端只发送输入指令（移动方向、技能按键），服务器在固定时间点收集所有玩家指令后广播统一帧数据。各客户端收到后 step 执行相同逻辑帧，产生一致的游戏状态。

```
Player A 输入 ──┐
Player B 输入 ──┤→ Server（收集→打包帧数据）→ Broadcast → 各端独立 step → 相同结果
Player C 输入 ──┘
```

### 状态同步（State Sync）

服务器运行完整游戏逻辑，计算权威结果后广播状态快照给各客户端。客户端主要做插值/预测来平滑显示。

```
Player A 输入 → Server（权威计算）→ State Snapshot → Broadcast → 各端插值渲染
```

## 带宽

| 维度 | 帧同步 | 状态同步 |
|------|--------|----------|
| 上行（客户端→服务器） | 极低——仅操作指令（几个字节/帧） | 低——操作指令 |
| 下行（服务器→客户端） | 低——统一帧数据（所有玩家操作合并），与在线人数成正比 | 中~高——状态快照（位置/血量/状态），与实体数成正比 |
| 同时在线容量 | 取决于操作数据量 × 玩家数，MOBA 10 人轻松 | 取决于实体状态量，M M O 千人需分区/优化 |
| 流量特征 | 稳定持续（固定逻辑帧率 ~15-30fps） | 可变（快照频率可调，静止实体不更新） |

> [!tip] 关键区别
> 帧同步的带宽瓶颈在于**玩家数量**（每个玩家都要广播操作），状态同步的瓶颈在于**实体数量**（每个实体都有状态字段）。MOBA 10 人对帧同步是天然优势；MMO 上千实体对状态同步更友好。

## 确定性要求

| 维度 | 帧同步 | 状态同步 |
|------|--------|----------|
| 确定性要求 | **极高**——所有客户端必须逐帧结果完全一致 | **低**——服务器是唯一权威，客户端只做表现 |
| 浮点数 | 禁止（必须用定点数） | 允许（客户端误差可被服务器修正） |
| 多线程 | 逻辑层禁止（单线程确定顺序） | 允许 |
| PRNG | 确定性种子 + 相同算法 | 无要求 |
| 容器遍历顺序 | 必须稳定（SortedDictionary 替代 Dictionary） | 无要求 |
| 跨平台一致性 | 需额外验证（iOS/Android/PC） | 不需要 |

> [!danger] 帧同步的两条铁律
> 1. **禁止使用 `float`**——必须用定点数（`Fix64`）。IEEE 754 在不同平台精度行为不一致。
> 2. **禁止逻辑层多线程**——确定顺序执行是确定性前提。

## 延迟与体验

| 维度 | 帧同步 | 状态同步 |
|------|--------|----------|
| 操作到反馈延迟 | 较高——需等待服务器广播下一帧（逻辑帧间隔 × RTT/2） | 较低——客户端可本地预测，服务器修正 |
| 客户端预测 | 复杂（预测回滚，需保存快照 + 重算） | 常规（Dead Reckoning / 插值） |
| 慢客户端影响 | 乐观帧锁定下无影响；严格锁定下拖慢所有人 | 无影响 |
| 断线重连 | 需补发缺失帧 → 快速追帧（跳帧循环） | 发送全量快照 → 重新同步 |
| 录像/回放 | **天然支持**（帧数据 = 操作序列，极小体积） | 需额外录制状态流，体积大 |

帧同步利用**预测回滚**隐藏延迟：客户端在未收到服务器数据前本地预测执行，收到后若不匹配则回滚重算。实现方式从手动快照到代码生成不等——代码生成方案（预编译生成 `SaveState()`/`LoadState()`）是生产环境的最佳实践。

## 反作弊

| 维度 | 帧同步 | 状态同步 |
|------|--------|----------|
| 全图可见（Map Hack） | **无法防御**——所有客户端拥有完整游戏状态才能计算 | 服务器只下发可见范围的状态 |
| 数值修改 | 难以防御——客户端知道所有单位状态 | 容易防御——服务器是唯一权威 |
| 自瞄/自动化 | 难以防御 | 可服务器端检测异常操作模式 |
| 核心策略 | 校验和比对 + 行为分析 + 录像审查 | 服务器权威 + 可见性裁剪 |

> [!warning] 帧同步的核心安全缺陷
> 帧同步要求所有客户端拥有完整游戏状态（才能确定性执行），因此**战争迷雾对反作弊无效**——客户端内存中已有全图数据，只是不在屏幕上渲染。MOBA 的反作弊依赖赛后录像审查 + 运行时校验和比对，而非实时拦截。

## 适用场景

### 帧同步适合

| 游戏类型 | 原因 |
|----------|------|
| MOBA（王者荣耀、Dota 2） | 10 人上限，带宽极低，操作密集型 |
| RTS（星际争霸、帝国时代） | 大量单位确定性计算，操作序列回放 |
| 格斗游戏 | 帧精确判定，超低响应延迟要求 |
| 回合制策略 | 天然适配 Lockstep，无实时延迟压力 |

### 状态同步适合

| 游戏类型 | 原因 |
|----------|------|
| FPS（CS:GO、Valorant） | 服务器权威命中判定，反作弊刚需 |
| M M O R P G（魔兽世界） | 海量实体，可见性裁剪，带宽可控 |
| 大逃杀（PUBG、Apex） | 百人同场 + 物理模拟 + 服务器权威 |
| 沙盒/生存（Minecraft 多人） | 世界状态庞大，增量同步 |

### 混合方案

部分游戏采用混合架构：核心战斗用帧同步，周边系统用状态同步。例如王者荣耀的战斗层是帧同步，社交/商城/匹配用的是标准 HTTP/状态同步。Dota 2 也采用了类似策略——战斗逻辑是服务器权威的 Lockstep 变体，非战斗状态由可靠消息传递。

## 决策指南

```
游戏人数 ≤ 10 且 操作密集型（MOBA/RTS）
  → 帧同步 — 带宽极低，回放天然支持

游戏人数 10~100 且 需要服务器权威判定（FPS）
  → 状态同步 — 反作弊刚需，预测平滑

游戏人数 > 100（MMO/大逃杀）
  → 状态同步 — 帧同步的操作广播在此规模性能崩溃

需要回放/观战功能
  → 帧同步天然优势 — 操作序列 = 完整对局记录
```
