## 一、核心思想

### 传统 RAG 的局限

传统 LLM 文档交互模式类似 RAG：上传文件 → 检索相关片段 → 生成答案。这种方式的问题是：

- **没有知识积累**：每次提问都需要从头发现和拼凑信息
- **无法处理复杂综合问题**：需要跨多个文档综合时，LLM 必须实时检索并拼接
- **NotebookLM、ChatGPT 文件上传等大多采用此模式**

### LLM Wiki 的不同之处

Karpathy 提出的核心创新：**让 LLM 增量式地构建和维护一个持久的 Wiki**。

当添加新来源时，LLM 不只是索引它，而是：

1. **阅读来源**，提取关键信息
2. **整合进现有 Wiki** —— 更新实体页面、修订主题摘要
3. **标记新旧数据之间的矛盾**
4. **强化或挑战不断演进的综合结论**

**关键区别**：Wiki 是一个**持久的、复合的工件**。交叉引用已经存在，矛盾已经被标记，综合结论已经反映了所有已读内容。

### 人类与 LLM 的分工

| 角色 | 职责 |
|------|------|
| 人类 | 策划来源、引导分析、提出好问题、思考意义 |
| LLM | 总结、交叉引用、归档、记账等所有体力活 |

Karpathy 的工作流：LLM Agent 在一边，Obsidian 在另一边。LLM 基于对话进行编辑，人类实时浏览结果——跟踪链接、查看图谱视图、阅读更新页面。

> "Obsidian 是 IDE；LLM 是程序员；Wiki 是代码库。"

### 适用场景

- **个人**：追踪目标、健康、心理学、自我提升
- **研究**：数周或数月深入一个主题，阅读论文、文章、报告
- **读书**：逐章归档，构建角色、主题、情节线索页面
- **商业/团队**：由 LLM 维护的内部 Wiki，输入 Slack 线程、会议记录、项目文档
- **竞争分析、尽职调查、旅行规划、课程笔记、爱好深度探索**

## 二、三层架构

```
┌─────────────────────────────────────┐
│  Schema (模式文件)                   │
│  CLAUDE.md / AGENTS.md              │
│  告诉 LLM Wiki 的结构、约定和工作流   │
└─────────────────────────────────────┘
           ↓
┌─────────────────────────────────────┐
│  The Wiki (Wiki 层)                  │
│  LLM 生成的 markdown 文件目录         │
│  摘要、实体页面、概念页面、比较等      │
│  LLM 完全拥有这一层                   │
└─────────────────────────────────────┘
           ↓
┌─────────────────────────────────────┐
│  Raw Sources (原始来源层)             │
│  策划的原始文档集合                   │
│  文章、论文、图片、数据文件            │
│  不可变 —— LLM 只读不写               │
└─────────────────────────────────────┘
```

### 1. Raw Sources（原始来源）

- 策划的原始文档集合
- 文章、论文、图片、数据文件
- **不可变** —— LLM 读取但不修改
- 这是你的**单一事实来源**

### 2. The Wiki（Wiki 层）

- LLM 生成的 markdown 文件目录
- 摘要、实体页面、概念页面、比较、概览、综合结论
- **LLM 完全拥有这一层**
- 创建页面、更新页面、维护交叉引用、保持一致性
- 人类阅读；LLM 写作

### 3. Schema（模式层）

- 告诉 LLM Wiki 如何结构化
- 约定是什么
- 摄取来源、回答问题、维护 Wiki 时的工作流
- **这是关键的配置文件**
- 使 LLM 成为有纪律的 Wiki 维护者，而非通用聊天机器人
- 你和 LLM 共同演化这一文件

## 三、三种操作

### 1. Ingest（摄取）

将新来源放入原始集合，告诉 LLM 处理它。

**示例流程**：
1. LLM 阅读来源
2. 与人类讨论关键要点
3. 在 Wiki 中写入摘要页面
4. 更新索引
5. 更新跨 Wiki 的相关实体和概念页面
6. 追加日志条目

**一个来源可能触及 10-15 个 Wiki 页面**。

Karpathy 偏好**一次摄取一个来源并保持参与** —— 阅读摘要、检查更新、引导 LLM 强调什么。但也可以批量摄取。

### 2. Query（查询）

针对 Wiki 提问。LLM 搜索相关页面、阅读它们、综合答案并引用来源。

**答案形式可以多样**：
- markdown 页面
- 比较表格
- 幻灯片 (Marp)
- 图表 (matplotlib)
- 画布

**重要洞察**：好的答案可以**归档回 Wiki 作为新页面**。你要求的比较、分析、发现的联系 —— 这些有价值，不应消失在聊天记录中。

### 3. Lint（检查）

定期让 LLM 健康检查 Wiki：

- 页面之间的矛盾
- 新来源已取代的陈旧声明
- 没有入站链接的孤立页面
- 被提及但缺乏自己页面的重要概念
- 缺失的交叉引用
- 可以通过网络搜索填补的数据缺口

LLM 善于建议要调查的新问题和要寻找的新来源。

## 四、索引与日志

### index.md（内容导向）

- Wiki 中所有内容的目录
- 每个页面列出：链接、一行摘要、可选元数据（日期、来源数）
- 按类别组织（实体、概念、来源等）
- LLM 每次摄取时更新
- 回答查询时，LLM 先读索引找到相关页面，再深入阅读
- 在中等规模（~100 来源，~数百页面）下效果很好
- **避免了基于嵌入的 RAG 基础设施需求**

### log.md（时间导向）

- 只追加的记录，记录发生了什么、何时发生
- 摄取、查询、检查操作
- **实用技巧**：如果每个条目以一致前缀开头（如 `## [2026-04-02] ingest | Article Title`），日志可以用简单 Unix 工具解析
  - `grep "^## \[" log.md | tail -5` 给出最后 5 条条目
- 提供 Wiki 演变的时间线
- 帮助 LLM 理解最近做了什么

## 五、可选工具

### 搜索工具

小规模时 index 文件足够，但 Wiki 增长后需要适当搜索。

- **qmd**：本地 markdown 文件搜索引擎，混合 BM25/向量搜索 + LLM 重排序，全设备端
  - 有 CLI（LLM 可以调用）和 MCP 服务器

### Obsidian 相关技巧

- **Obsidian Web Clipper**：浏览器扩展，将网页文章转换为 markdown
- **本地下载图片**：Obsidian 设置 → 文件和链接 → 设置附件文件夹路径 → 绑定热键下载附件
  - 让 LLM 直接查看和引用图片，而非依赖可能失效的 URL
- **Obsidian 图谱视图**：查看 Wiki 形状的最佳方式——什么连接到什么、哪些是枢纽、哪些是孤立节点
- **Marp**：基于 markdown 的幻灯片格式，Obsidian 有插件
- **Dataview**：Obsidian 插件，运行 frontmatter 查询，生成动态表格和列表

### Git 优势

Wiki 只是 markdown 文件的 git 仓库。免费获得版本历史、分支和协作。

## 六、为什么有效

维护知识库的繁琐部分**不是阅读或思考，而是记账**：

- 更新交叉引用
- 保持摘要最新
- 标记新数据何时与旧声明矛盾
- 在数十个页面间保持一致性

**人类放弃 Wiki 是因为维护负担增长快于价值。LLM 不会厌倦、不会忘记更新交叉引用、可以一次触及 15 个文件。Wiki 保持维护，因为维护成本接近零。**

人类的职责：策划来源、指导分析、提出好问题、思考一切意味着什么。LLM 的职责：其他一切。

### 与 Memex 的联系

这一想法在精神上与 Vannevar Bush 的 Memex（1945）相关——一个个人的、策划的知识存储，文档之间有联想轨迹。Bush 的愿景更接近此而非网络所变成的样子：私人的、主动策划的、文档间连接与文档本身同等有价值。**他没能解决的部分是谁来做维护。LLM 解决了这个问题。**

---

## 七、关键启示

1. **知识应该被编译一次，然后保持更新**，而不是每次查询时重新推导
2. **Wiki 作为复合工件**：每次添加来源和提问都会让它更丰富
3. **人类在循环中**：负责策展和提问，而非写作和维护
4. **三层架构清晰分离**：原始来源（不可变）、Wiki（LLM 拥有）、Schema（配置约定）
5. **index.md + log.md 是导航关键**：避免复杂基础设施
6. **查询的答案可以归档回 Wiki**：探索也应复合积累
7. **lint 是健康机制**：主动发现矛盾、陈旧、孤立、缺口

## 八、备注

本文档有意抽象。它描述的是想法，而非具体实现。确切的目录结构、模式约定、页面格式、工具——所有这些都取决于你的领域、偏好和选择的 LLM。一切都是可选和模块化的：选择有用的，忽略不需要的。正确用法是与你的 LLM Agent 分享它，共同实例化适合你需求的版本。
